# 源码包与透明加密核查

本记录说明源码交付的字节完整性检查及其边界。检查不读取业务文件、真实密钥、证书库或终端策略，不关闭或绕过加密软件，也不调整系统权限。发布前应检查 Git 实际内容并确认公开权利。

## 已观察到的结果

- 原始交付 ZIP 大小 47,152 字节，SHA-256 为 `53fb9fcd4454ede2be94a010f2a07d15e744e9f5646a38ce2d55e52c1ccb5e3e`，与打包记录一致。它是首次本地交付快照；后续 CI 文档不在该原始快照中。
- 普通文件 API 所呈现的 ZIP 以 `PK 03 04` 开始，首条目偏移为 0；中央目录可直接解析，归档结束记录位于文件末尾，没有前缀包装或尾部附加数据。
- 21 个条目均使用 Deflate（方法 8）。中央和本地头的标准加密、强加密与遮蔽头标记均未设置；所有条目的额外字段为空，CRC 检查全部通过，无需 ZIP 密码。
- 21 个归档条目均可严格按 UTF-8 解码，无 NUL 或异常控制字符；10 个 C# 文件具有预期源码结构，5 个 XML 配置/项目文件可解析。归档内未见 TSD 包装头，未包含 `.dpapi` 或 `.lkmbackup` 运行数据。
- ZIP 与 21 个对应文件的 Windows 属性均未标记 `FILE_ATTRIBUTE_ENCRYPTED`（0x4000）。这只说明未报告 Windows EFS 文件属性，不能用来排除第三方加密。
- 不同读取进程、导出工具和存储策略可能呈现不同的字节流。应在各自交付边界独立检查可读性；本仓库不保留个人或组织终端环境的调查记录。

## 四种含义须区分

| 类型 | 本次结论 |
| --- | --- |
| ZIP 自身的密码/条目加密 | 在当前 API 呈现的归档流中未使用；头标记、压缩方式和无密码 CRC/文本检查相互印证。 |
| Windows EFS | ZIP 与对应文件未报告 Encrypted 属性。ZIP 文档里的 bit 11 “EFS”是 UTF-8 文件名编码标记，和 Windows EFS 文件加密不是同一概念。 |
| 第三方终端透明处理 | 未评估个人或组织的终端策略。单个进程可读、可以编译或未设置 EFS 属性，都不足以证明其他存储、导出或分发边界的状态与授权。 |
| 本程序的 DPAPI | 只用于运行时密钥库与完整备份；源码 ZIP 不含这些运行数据，程序没有给源码包增加 DPAPI 加密。 |

检查与后续 Git/CI 只能确认各自读取到或上传的内容。GitHub 独立 runner 的读取与编译结果只覆盖对应提交和检查，不能证明个人或组织终端的策略状态，也不替代来源与再分发授权确认。本项目不包含解密、禁用加密软件或规避公司策略的发布步骤。

参考：[ZIP 格式规范](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)、[Windows 文件属性](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants)。
